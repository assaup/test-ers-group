# 001. Серверные сессии в SQLite вместо JWT

**Статус:** принято

## Контекст

Нужны вход, выход и защита API. Клиент и сервер работают на одном origin (прокси Vite в разработке,
Express отдаёт статику в production).

## Решение

- При входе сервер генерирует токен `crypto.randomBytes(32)` (base64url) и отдаёт его в cookie `sid`
  (`httpOnly`, `SameSite=Lax`, `Secure` в production, срок 7 дней).
- В таблицу `sessions` пишется не сам токен, а `sha256(token)` и `expires_at`.
- `requireAuth` хеширует токен из cookie, ищет сессию с непросроченным сроком и кладёт пользователя
  в `req.user`.
- Выход удаляет строку из `sessions` и очищает cookie.

## Альтернативы

- **JWT в `localStorage`** — токен доступен любому JS на странице, XSS = кража сессии.
- **JWT в httpOnly-cookie** — от XSS защищает, но выход не отзывает токен: до истечения срока он
  остаётся валидным. Для честного logout нужен denylist в БД — то есть та же таблица сессий, только
  сложнее.
- **express-session** — делает то же самое, но прячет логику; своя реализация занимает ~50 строк и
  её проще объяснить.

## Последствия

- Выход и отзыв сессии работают мгновенно.
- Утечка базы не даёт рабочих токенов — в ней только хеши.
- Каждый защищённый запрос — один индексированный `SELECT` в SQLite; для этого масштаба бесплатно.
- `SameSite=Lax` закрывает CSRF для `POST`-запросов с чужих сайтов; отдельный CSRF-токен — в
  возможном развитии.
